## RISKY — needs your decision

### Finding 16 — `daily-close-lines-capture` runs a command that can never do anything

`evmax cleanup close-lines` selects rows from `ev_outcomes` where `outcome IS NULL`, but a row
only enters `ev_outcomes` when it is resolved (non-NULL outcome). The predicate is unsatisfiable:

```
ev_outcomes total rows:                 3227
ev_outcomes with outcome IS NULL:          0
close-lines candidate rows (any date):     0
rows that DO have pinnacle_close_prob:  1834   <- all from watch-closes + backfill_clv
```

I did **not** touch this. It is exactly the case the audit spec calls out: the code, not the
doc, looks like the thing that drifted, so rewriting the doc around it would bless a bug.
Three options, in my recommended order:

1. **Fix the query** — if the intent is "capture closes for markets that haven't resolved yet",
   the source table should be `ev_predictions` LEFT JOIN `ev_outcomes` (pending = no outcome row
   at all), not an inner join demanding a NULL outcome inside `ev_outcomes`. This makes the daily
   task do real work and gives close capture a second, app-independent path.
2. **Delete the command and the task** — `watch-closes` under launchd already produces the
   closes, and it runs every 5 minutes whether or not the desktop app is open. This is the
   honest option if close capture is considered solved.
3. **Leave it, document it as a no-op** — cheapest, but it keeps a daily task burning a run slot
   to do nothing, and the doc currently implies it is the primary capture mechanism.

Worth noting this is consistent with a previously-recorded observation that the command is
dead; this audit adds the empirical row counts.
